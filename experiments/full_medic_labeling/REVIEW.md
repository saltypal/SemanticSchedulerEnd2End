## Confirmed blockers in the inspected helpers

1. **P1 — Feature resume can mix encoder revisions.** `training.py:82–88` keys progress by row IDs/roles, encoder name and this file's hash, then calls unpinned `load_encoder(name)` and overwrites identity. A resumed partial bank can retain shards from revision A and append revision B. Existing arrays are accepted based on file existence without persisted completed-shard checksums, expected shapes/dtypes or finite-value validation. Pin the initial encoder/processor/implementation identity before extraction, enforce it on resume, and validate persisted shard/bank evidence before reuse. Hashing the completed bank afterwards does not detect that it contains mixed producers.
2. **P1 — Training completion gate is insufficient.** `training.py:19–28` validates the checkpoint file against its supplied manifest and checks item split counts. It does not verify checkpoint identity against the approved dataset/model/prompt/producer contract, SQLite integrity, or that every item joins a recorded prediction. A different full-count checkpoint, or one with orphan items, can pass. Validate identity, expected source coverage and joined outcomes; preserve unavailable results explicitly rather than silently treating missing outcomes as completion. Full available labels need not be required if the approved protocol permits recorded failures, but the distinction must be explicit.
3. **P1 — Session wall bound is not enforced around expensive stages.** `campaign.py:160` downloads each next shard before checking the deadline at line 166; restored items are skipped before that check. It can download/scan many already-completed shards after the deadline, and periodic full exports/backups occur outside the remaining-time check. Two pending generation calls can also drain after cutoff. Gate before downloads/next shard/checkpoints, reserve bounded drain/export time, and disclose that generation max_time is a soft stopping control. The 12,600-second / seven aggregate GPU-hour allowance must include model setup and durable output packaging, not just the inner row loop.

## Mechanisms that look sound within inspected scope

- SQLite has one application writer; per-item inserts are transactional. `sqlite3.backup` creates the exported checkpoint, avoiding unsafe copies of a live WAL database. Exported labels, CSV and progress are subsequently bound by the checkpoint manifest. Duplicate image predictions are keyed by byte hash while source aliases remain individual items.
- Exact copies crossing native splits receive the most reserved role; native test hashes are excluded from the training records. `source_item` may still point at the first duplicate occurrence, but its identical bytes are hash-checked during extraction. This is valid exact-content exclusion, not verified near-view/event independence.
- `BatchBank.subset` composes global row indices lazily; minibatch indexing maps to the underlying array and converts only selected rows to float32/bool. Shared `feature_subset` preserves this behavior in token fitting/prediction. No immediate lazy-index ordering bug was found by inspection. Float16 token storage introduces a numerical change and needs finite checks after conversion plus parity against a small float32 reference.
- The rubric is a system message; only the image and generic assessment request enter the user message. Native image annotations are retained as provenance, not supplied to the teacher. Teacher failures remain unavailable outcomes rather than forced Low labels. Schema parsing and finite-logit checks are present.
- `coverage_complete` currently means every source row has a recorded outcome, not every outcome is available. Terminal/report wording must preserve this distinction; `all_labels_available` is separately recorded. Current rows with failed predictions remain permanently skipped on resume, so recovery needs an explicit bounded retry mechanism if failures are to be revisited.

## Bounded preflight decision

A 12-image cloud preflight is a reasonable next validation scope **after** the intended device orchestrator and explicit preflight entry point are implemented and locally checked. The current notebook has no runnable preflight path; removing its guard alone is insufficient. The preflight should enforce an actual 12-source-row cap, log each stage, verify GPU placement/system prompt/pixels, exercise exact duplicate accounting, save and reopen the backup, resume without duplicate inference, and compare lazy-token minibatches with their direct reference. It must stop before student training unless that tiny integration check is separately part of its explicit scope. Pin/verify the managed source manifest and runtime before models load; the current notebook only checks that a source file exists and prints versions, which does not establish approved source identity or compatible dependencies.

No full campaign, complete dataset labeling, model accuracy, persistence recovery or cost result is established by this assessment. Tests were inspected, not rerun. Existing explicit build guard should remain until the completed orchestrator and resume preflight meet their acceptance checks.
